# 미리봄 UI 재설계 — 고령층 친화 안내서 (설계 문서)

- 작성일: 2026-07-30
- 대상 브랜치: `work`
- 근거 기준: 서울시 「고령층 친화 디지털 접근성 표준」 10개 항목

## 1. 배경과 목표

미리봄은 병원 안내문(사진/PDF)을 업로드하면 AI가 어르신이 이해하기 쉬운 그림 안내서로
바꿔주는 서비스다. 현재 흐름은 **업로드 → 내용확인 → 맞춤질문 → 안내서** 4단계로,
단계가 많고 개인화 질문과 결과가 분리되어 있다.

목표: 흐름을 단순화하고, 개인화(맞춤 질문)를 안내서 안으로 통합하여
"질문에 답하면 그에 맞는 안내문이 즉시 나타나거나 숨겨지는" 형태로 재설계한다.
서울시 고령층 친화 디지털 접근성 표준 10개 항목을 설계 기준으로 삼는다.

### 설계 기준 (서울시 「고령층 친화 디지털 접근성 표준」)

1. 글자는 크고 선명하게 — 크고 굵게, 확대해도 안 깨지게, 명도·색상 대비 뚜렷, 필기체 지양
2. 필수 요소만 구성 — 과업과 무관한 요소 제거
3. 단순·친숙한 정보 구조 — 얕은 계층, 학습된 UX 활용
4. 쉬운 용어 — 외국어·약어 지양, 한글 우선, 용어 일관, 전문어는 친절히 설명
5. 가시적 시스템 상태 — 이전·현재·다음 파악, 컨트롤 1개 = 기능 1개
6. 컨트롤은 행동 유발 — 기능 있는/없는 요소 명확 구분
7. 신속·정확 조작 — 손떨림·저시력 고려, 크기·간격 충분, 복잡한 동작 지양
8. 즉각 피드백 — 선택 시 효과·결과 즉시, 시각·청각·촉각 활용
9. 오류 예방·복구 — 사전 경고, 취소·이전 상태 복구
10. 심리적 부담 감소 — 친절한 도움말, 문제 시 즉시 연락 방법 제공

## 2. 결정 사항 (확정)

- **내용확인 단계**: 별도 단계 제거. 대신 안내서 상단 제목 옆 "고치기" 버튼으로
  검사명·병원·날짜·시간을 그 자리에서 수정 가능 (표준 9 유지).
- **"아니오" 동작**: 해당 안내문을 **숨김**. 언제든 "네"로 바꾸면 다시 나타남
  (영구 삭제 아님, 표준 9 오류복구).
- **맞춤 질문 위치**: 안내서 **맨 위 "나에게 맞추기" 묶음**에 배치.
- **개인화 구현 방식**: A안 — 서버가 해당 가능한 모든 안내문을 미리 생성하고
  각 페이지에 "어느 질문의 어느 답에서 켜지는지" 태그를 붙인다.
  화면에서 답에 따라 즉시 보이기/숨기기 (네트워크 재호출 없음).

## 3. 화면 흐름

```
[기존] 업로드 → 내용확인 → 맞춤질문 → 안내서
[신규] 업로드 → (만드는 중…) → 쉬운 안내서 (맞춤 질문 · 고치기 내장)
```

- `AppStep`: `"upload" | "review" | "questions" | "guide"` → `"upload" | "guide"` 로 축소.
- 업로드 후 파이프라인(parse → analyze → finalize)을 자동 연속 실행하여
  중간 단계 없이 안내서로 진입.
- 진행 표시(`ProgressHeader`): **안내문 올리기 → 만드는 중 → 쉬운 안내서 → PDF 저장**
  으로 단순화 (표준 5).

## 4. 안내서 맨 위 "나에게 맞추기" 묶음

- 질문 카드들을 안내서 최상단에 배치.
- 각 질문은 큰 버튼: **네 / 아니오 / 잘 모르겠어요**.
  - 선택지가 여러 개인 질문(피 멎는 약 개수: 안 먹어요/한 가지/두 가지 이상,
    검사 시간: 오전/오후)은 그대로 여러 버튼으로 표시.
- 동작 규칙:
  - 공통 안내문(`applicability === "all"`)은 항상 표시.
  - 조건부 안내문은 매칭되는 답을 고르면 아래에 **나타남**, 아니오/비매칭이면 **숨김**.
  - 되돌리기 가능(답을 바꾸면 즉시 반영).
- 표준 9(오류 예방·복구): 아직 답하지 않은 질문은 "아직 안 골랐어요"로 눈에 띄게 표시.
  미응답으로 인해 숨겨진 안내가 있으면 부드럽게 알림.
- 표준 8(즉각 피드백): 답 선택 시 해당 카드 강조 + 짧은 문구
  ("이 안내를 추가했어요" / "이 안내를 숨겼어요") + 선택적 음성 읽기.

## 5. 안내서 내 "고치기" 및 도움/연락

- 상단 제목 옆 **고치기** 버튼 → 검사명·병원·날짜·시간을 인라인 수정
  (기존 `ReviewStep`의 입력 UI 재활용, 표준 9).
- 항상 보이는 **병원에 전화하기** 버튼: 파싱된 `document.hospital_phone` 사용.
- 친절한 도움말 한 줄 상시 노출 (표준 10: 심리적 부담 감소).

## 6. 글자·컨트롤 표준화

- 기본 글자 16px → **18px**.
- 크기 옵션(보통/크게/더 크게)을 **1.0 / 1.25 / 1.5배**로 상향.
- 16px 미만 보조 텍스트(안전문구 0.84rem, 근거·파일명 0.85rem 등) 전부 상향 (표준 1).
- 접근성 설정(글자 크기·고대비)을 **`localStorage`에 저장** → 재방문 시 유지.
- 폰트는 Pretendard 유지 (필기체 없음, 표준 1).
- 기능 없는 요소는 버튼처럼 보이지 않게 (표준 6).
- 버튼 크기·간격은 현재의 넉넉한 수준 유지 (표준 7).

## 7. 데이터 모델 변경

`GuidePage`는 이미 `personalized_by: string[]`(question_id)와 `personalized` 필드를 가진다.
A안을 위해 각 페이지가 "어느 답에서 활성화되는지"를 담도록 확장한다.

- `GuidePage`에 활성화 조건 추가 (예: `activation?: { question_id: string; values: string[] }`).
  - `values`: 이 페이지를 보이게 하는 답의 값 목록 (예: 혈압약 → `["yes"]`).
  - 공통 안내문은 `activation` 없음 → 항상 표시.
- `buildFinalGuide`: 답으로 사전 필터링하지 않고 **조건부 안내문을 모두 포함**하여 생성.
  각 페이지에 `activation`을 채운다.
- `finalize` API: 화면에서 **빈 answers(`{}`)로 호출**한다. `buildFinalGuide`는 answers와
  무관하게 모든 조건부 안내문을 포함해 생성한다(사전 필터링 제거).
- "confirm"(잘 모르겠어요/병원 확인) 처리: 기존에 `answerApplies`가 `confirm`으로 분류해
  `hospital_confirmation` 목록으로 보내던 항목은, 신규 모델에서 해당 질문의 답이
  "잘 모르겠어요/미매칭"일 때 화면에서 "병원에 확인" 표시로 노출한다.
  구체 매핑은 구현 계획에서 확정한다.
- 화면(`page.tsx` / `GuideStep`)이 answers 상태를 들고 `activation`으로 표시 여부 필터링.

## 8. 손대는 파일

- `app/page.tsx` — 흐름 단순화, 자동 파이프라인, 맞춤 답변 상태 및 필터링
- `app/lib/guide-generator.ts` — 전부 생성 + `activation` 태그
- `app/lib/types.ts` — `AppStep` 축소, `GuidePage.activation` 추가
- `app/ui/GuideStep.tsx` — "나에게 맞추기" 묶음, 고치기, 병원 연락 통합
- `app/ui/ProgressHeader.tsx` — 단계 단순화
- `app/globals.css` — 글자 스케일, 보조 텍스트 상향, 맞춤 묶음 스타일
- 제거: `app/ui/ReviewStep.tsx`, `app/ui/QuestionStep.tsx`

## 9. 오류 처리

- 파이프라인(parse/analyze/finalize) 실패 시: 기존 `globalError` 방식 유지,
  친절한 문구 + 다시 시도(표준 9·10).
- 조건부 안내문이 전혀 없을 경우: "나에게 맞추기" 묶음을 숨기고 안내서만 표시.
- OCR 신뢰도 경고(`source_reliability`, `warnings`)는 안내서 상단에 부드럽게 표시.

## 10. 범위 밖 (YAGNI)

- 챗봇(`GuideChat`)·PDF 저장·음성 읽기 등 기존 기능은 유지하되 이번 재설계의 핵심 변경 대상 아님.
- 서버 파싱/추출 로직(`parse`, `analyze`, `information-extract`)의 내부 알고리즘은 변경하지 않음.
- 백엔드 API 신규 추가 없음(기존 라우트 재활용).
